===== 014 | CODEX =====

Podemos trabalhar com **um agente com chamadas de ferramentas (*function calling*)**, usando funções Python para consultar as informações da loja. É uma abordagem simples e adequada ao problema.

O fluxo seria:

1. O cliente envia uma mensagem pelo Streamlit.
2. O modelo identifica se precisa consultar alguma informação.
3. Uma função Python faz a consulta nos dados ou nas políticas.
4. O modelo usa o resultado para responder no tom da loja.

Por exemplo, para “Quais violões disponíveis custam até R$ 1.000?”, o modelo chama uma ferramenta como `buscar_produtos`, com categoria e preço máximo. O Python filtra os dados e retorna os produtos encontrados. O modelo transforma esse resultado em uma resposta natural.

Começaríamos com poucas ferramentas, ajustadas ao conteúdo dos arquivos:

| Ferramenta | Finalidade |
|---|---|
| Buscar produtos | Consultar catálogo, preços e disponibilidade |
| Consultar pedido | Buscar o status de um pedido |
| Consultar políticas | Obter informações sobre horários, pagamentos, trocas e devoluções |

**Não precisamos escolher um framework de agentes agora.** Podemos implementar esse ciclo diretamente com o SDK do provedor do modelo e funções Python. Também não precisamos assumir um banco vetorial: se o manual for pequeno, uma consulta simples ao conteúdo pode ser suficiente. A leitura dos arquivos vai orientar essa decisão.

Até aqui, nossas decisões ficariam assim:

| Decisão técnica | Proposta inicial |
|---|---|
| Framework / abordagem | Chamadas de ferramentas, com funções Python e SDK do provedor |
| Modelo e provedor | Ainda a definir |
| Interface | Chat local no navegador com Streamlit |
| Histórico | Mantido durante a sessão com `st.session_state`, sem banco |
| Tratamento dos dados | Carregar e normalizar CSVs; extrair o texto do PDF de políticas |

Um ajuste no termo **offline**: o Streamlit roda localmente, mas, se escolhermos um modelo por API, o agente precisará de internet. Para funcionar totalmente offline, precisaríamos executar o modelo na sua máquina.

Minha preferência inicial é **Streamlit + modelo por API + ferramentas Python**, pela simplicidade de implementação. Isso já permite demonstrar a principal competência pedida: o agente decidir quando consultar informações e responder com base nos resultados.

**Você pode continuar trabalhando localmente e subir tudo quando estiver pronto.** O requisito é manter um histórico de commits com progresso real; ele não exige enviar cada commit ao GitHub imediatamente.

A diferença é:

- **Commit:** registra uma etapa do trabalho na sua máquina.
- **Push:** envia os commits locais para o GitHub.

Podemos fazer commits locais conforme concluirmos etapas, por exemplo:

1. Escopo e estrutura inicial.
2. Consultas aos dados e às políticas.
3. Agente com chamadas de ferramentas.
4. Chat em Streamlit.
5. Validação, exemplos de conversa e documentação.

Quando estiver tudo funcionando, você cria o repositório público e faz **um único push contendo todo esse histórico**. O GitHub mostrará os commits individuais normalmente.

O importante é registrar o progresso durante o desenvolvimento, sem deixar para fabricar esse histórico no final ou juntar tudo em um único commit. Depois da entrega, encerramos as alterações no repositório.

Assim, **seu fluxo local permanece praticamente igual**: só precisamos criar os commits nos momentos adequados.
